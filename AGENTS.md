# نفّذها (Nafizha) — nafizha.com

Arabic-first services marketplace + LMS + marketing tools. Repo/DB name is `marwa_services`.

## Stack
- Laravel 11 (old-style skeleton: `app/Http/Kernel.php`, `app/Console/Kernel.php`, `RouteServiceProvider`), PHP 8.2+ (local: Herd Lite PHP 8.3)
- Livewire 3 + Alpine.js, Blade views, Vite
- MySQL, Pusher (broadcast/chat), EasyKash (payments), OpenAI (`openai-php/laravel`), Google API (Gmail + Sheets), Socialite
- Localization via `mcamara/laravel-localization` (`lang/ar`, `lang/en`); UI text is mostly Arabic

## Layout
- `routes/web.php` — public site + user area (wrapped in localization group). It `include`s `routes/admin.php` at the end.
- `routes/admin.php` — admin panel under `/admin`.
- Controllers: `app/Http/Controllers/front/*` (site), `app/Http/Controllers/admin/*` (panel), `api/EmailTrackingController` (open/click tracking).
- Models: `app/Models/front/*`, `app/Models/admin/*`, plus top-level models for newer features (Email*, Social*, NewCourse*, Testimonial, User).
- Views: `resources/views/website/*`, `resources/views/admin/*`.
- Uploaded files live under `public/uploads` (committed to git in places).
- Navbar (client file «تعديلات», item 02): «المستقلين» (`freelancers.index`, the approved-freelancers directory) and «المدونة» (`blogCategories` = `/blog`; `/categories` is the service categories page) replaced the course links; course links are not shown anywhere (pages still exist by URL). Homepage payment row shows EasyKash methods only.

## Feature areas
- Services/categories, cart & EasyKash checkout, digital products
- Jobs, packages/subscriptions (the old projects & offers system is gone; see Service request system)
- Courses: legacy `courses` and the newer `new-courses` (course → topic → lesson; video protected by `VideoProtectionMiddleware`)
- Properties & property maintenance, blog, portfolio, reviews/testimonials
- Chat (Livewire `app/Livewire/Chat` + Pusher), support tickets, user balance & withdrawals
- **Social media publishing** (`app/Services/SocialMedia/Platforms`: Facebook, Instagram, LinkedIn, TikTok, Twitter, YouTube) via `PublishSocialPostJob`
- **Email marketing** (MailMentor-like, client request): lists/contacts, templates, campaigns with A/B, drip, throttling, follow-ups, tracking, analytics, Gmail sending, Google Sheets import, AI writing (`app/Services/Email*`, `app/Jobs/*Campaign*`)

## Service request system (replaced the old projects/offers system)
- Spec: client PDF «رسم مسار العميل والأدمن والمستقلين»; built in phases (0 accounts/specializations ✓, 1 form builder ✓, 2 request page ✓, 3 freelancer board + offers + chat ✓, 4 payment/escrow + completion ✓, 5 admin tools ✓, 6 client classifications + client↔team messages ✓, 7 old projects/offers removed ✓ (tables dropped by `2026_10_17_100000_drop_old_projects_system`; `projects`, `project/*`, `my/project/*`, `admin/projects` redirect 301). Still to come from the client: the other two homepage cards («شخّص مشروعك مجانًا», «مشروعك ما بيوقف»).
- Requests: `ServiceRequest` (number `REQ-<1000+id>`, route key = number; path execute|explore; status open|inquiry; contact_* never shown to freelancers; filter columns budget_min/max, deadline, project_type, work_mode, city, urgency, experience) → `ServiceRequestAnswer` (snapshot of section/label/type + JSON value) and `ServiceRequestFile` (private `local` disk under `service-requests/<id>/`, downloaded through `requests.file`).
- `App\Services\ServiceRequests\RequestSubmission` = server-side visibility + validation + storing; keep it in sync with the JS. Client pages: `request` (create), `my/requests` (`front/ServiceRequestController`), clients only.
- Request forms: one main `ServiceForm` per sub-category (draft/published/paused; query with `ServiceForm::main()` — a published form may also have one draft revision, `revision_of_id`, edited in the builder `admin/request-forms/{form}/builder` and swapped in by `publishRevision()`) → `ServiceFormSection` → `ServiceFormQuestion` (12 types in `ServiceFormQuestion::TYPES`, `options`/`settings`/`condition`/`filter_key` columns). Admin builder at `admin/request-forms` (`admin/ServiceForm*Controller`).
- A question's `condition` = `{question_id, values[], negate}`: shown only when the source question is visible, answered, and its answer matches (or, with negate, doesn't match). `public/assets/website/js/service-request-form.js` implements this client-side; server validation must apply the same rule.
- Client-facing form markup is shared: `resources/views/website/service-requests/partials/{form-fields,question}.blade.php` (inputs `answers[<id>]`, files `answer_files[<id>][]`).
- Offers: `RequestOffer` (one per freelancer per request, unique; status new→viewed→in_discussion, withdrawn; accepted/rejected come with payment), `RequestOfferFile` (private disk), `OfferMessage` (conversation per offer, stores request + offer ids). Freelancer pages: `client-requests` board/detail, `my/offers` (`front/FreelancerRequestController`); shared chat/files/save: `front/OfferController`. Visibility: `ServiceRequest::scopeForFreelancer()` / `visibleToFreelancer()`; contact_* fields are never rendered on freelancer pages.
- **All payments on the site go through EasyKash** (same integration as the AyaKids project, own Nafizha account), in EGP — Stripe was removed completely (package, routes, views). Every payment is an `online_payments` row (`App\Models\OnlinePayment`; its id = EasyKash customerReference) with a `purpose`: `request` (escrow below), `service_order` (one service from its page or the whole cart — `checkout/order`; payload `items` with prices from the DB, cart emptied once paid; the buyer pays the service prices and the commission comes out of the sellers' share), `product_order`, `package`, `course`, `balance`. `App\Services\Payments\OnlinePaymentService` — `start`/`create`+`checkout`, `sync` (inquiry), `apply` (idempotent: marks paid once under a row lock and calls the purpose's `paid()` inside the same transaction; refuses an amount below the price; a late failure never undoes a payment). Applied from the return page `payments.return` (`payments/return/{id}/{return_token}` — the token replaces the session, the query string is never trusted), `easykash/webhook` (`OnlinePaymentController`, CSRF-exempt, outside the locale group; the payload is only a trigger — the payment is always confirmed by an EasyKash inquiry; the HMAC signature is checked only when `EASYKASH_HMAC_SECRET` is set, which the EasyKash dashboard may not offer) and `payments:sync` every 5 min (Fawry/wallet payments can complete hours later). Purposes implement `App\Services\Payments\PaymentPurpose` (`paid`, `failed`, `response`); the direct purchases live in `App\Services\Payments\Purposes\*` (extend `SitePurpose`; mails/notifications are sent via `afterCommit` so a mail failure never undoes a payment; commission rate is snapshotted in the payload). Prices of services/products/courses/packages are treated as EGP and shown with ج.م. Request escrow: `RequestPaymentService` (also the `request` purpose) — `startCheckout` (pending `RequestPayment` + its OnlinePayment, `request_payments.online_payment_id`, `gateway_reference` = that id), `fulfill` (test helper → `apply`), a payment for an already-taken request becomes `conflict` = needs refund, `deliver`, `release` (freelancer `users.balance` += amount − commission, `settings.website_balance` += commission, rows in `wallet_transactions`), static `commissionRate()` (admin setting, default 10%). EasyKash has no refund API: refunds are done in the EasyKash dashboard and confirmed by the admin (`refund_reference = manual`). Gateway interface `PaymentGateway` (takes an `OnlinePayment`) → `EasyKashPaymentGateway` (config `services.easykash`: EASYKASH_API_KEY, optional EASYKASH_HMAC_SECRET); tests bind `Tests\Fakes\FakePaymentGateway`. Amounts are shown with `App\Support\Money::format()`. Request statuses: open → in_progress → completed.
- Admin tools: `admin/requests?tab=active|inquiries|followup|completed|not_completed|refunds` + `admin/requests/{number}` (`admin/ServiceRequestAdminController`), actions in `App\Services\ServiceRequests\RequestAdminService` (close with `ServiceRequest::CLOSE_REASONS` → status not_completed, refunds held money first via `RequestPaymentService::refund`; publish inquiry with client consent; complete on behalf; follow-up). `requests:alert-no-offers` (scheduled every minute) alerts admins once per request after 60 min without offers; the first offer afterwards marks the follow-up resolved. Admin header bell = `admin/layouts/partials/notifications`. Clients can cancel open/inquiry requests (`requests.cancel`).
- History: `ServiceRequestEvent` (`service_request_events`) logs creation, every status change (model `updated` hook; actor = logged-in user, null = system; set `$request->statusChangeNote` before an update to attach a note), follow-up updates, admin notes and invitations; shown as «سجل الطلب» on the admin request page. Admins see matching freelancers of an open request and invite each once (`RequestAdminService::matchingFreelancers/invite`, route `admin.requests.invite`). Optional `service_requests.contact_method` (`ServiceRequest::CONTACT_METHODS`). Client offer tabs: all/new/saved/discussion/selected/rejected.
- Admin guide page: `admin/requests-guide` (`admin/service-requests/guide.blade.php`) — keep it in sync when behaviour changes. Demo data (non-production only): `php artisan db:seed --class=ServiceRequestsDemoSeeder` (accounts demo-*@nafizha.test, password `password`).
- The request page autosaves a draft (not files) in localStorage `rf-draft:<user id>`, restored on return and cleared after a successful submit (`request_created` flash).
- Client↔team messages: `RequestAdminMessage` (per request, `from_admin`), boxes on the client request page (`requests.messages.store`) and the admin request page (`admin.requests.messages.store`); never shown to freelancers.
- Client classifications: `App\Services\ServiceRequests\ClientClassifier` computes the 7 categories (fixed order in `CATEGORIES`) from requests + who spoke last in each team conversation; repeat threshold = `settings.repeat_client_threshold`. Admin pages `admin/clients`, `admin/clients/{user}` (`admin/ClientController`).
- Email per notification type is a site setting (`settings.request_notification_emails`, `App\Services\ServiceRequests\NotificationSettings`); each notification class names its `$emailKey`. Client classifications are cached 5 min (`ClientClassifier::cached()`), cleared by ServiceRequest / RequestAdminMessage / Setting model events.
- Notifications for this system extend `App\Notifications\ServiceRequestNotification` (data `text` + `url` path; bell entry sync, email queued). The navbar bell renders any notification with `data.url` generically and opens it via `notifications.open` (marks read, same-site paths only).
- Site CSS: the theme's forced white button text (`button { color:#fff !important }`) skips classes starting with `rf-`, so request-system buttons set their own colours; laravel-notify's CSS is loaded before the theme (website + admin). The theme still styles every `[type=radio|checkbox] + label` — scope new styles under a container class (see `.rf-*` / `.account-type-*` in `public/assets/website/css/styles.css`).

## Services page and help requests (client brief «متطلبات تطوير قسم الخدمات»)
- `/services` (`front/ServicesPageController`, view `website/services-catalog/index`): groups = `categories`, services = `sub_categories` (same records as the request system), ordered by `sort_order`, only `status = 1` (an admin previewing content also sees hidden ones). Instant client-side search, accordion, choice dialog (bottom sheet on phones): «أطلب الخدمة» → `SubCategory::requestUrl()` (admin `link`, else `requests.create?service=id`); «ساعدوني أختار» → help form. Page texts are content areas `services.page|choice|help`.
- Seed the 41 services / 6 groups: `php artisan db:seed --class=ServicesCatalogSeeder` (idempotent by name).
- Help requests (`HelpRequest`, number `HLP-<1000+id>`, statuses new/following/contacted/closed, `HelpRequestNote` internal notes) require login (user decision, overriding the brief), throttled 5/hour, notify admins (`HelpRequestNotification`, email key `help_requests`). Admin box `admin/help-requests` (search, filters, assign to an admin → notified, wa.me button). Never mixed with `ServiceRequest`.
- Admin catalog `admin/catalog/groups|services` (`admin/CatalogController`): add/edit/hide, inline new group, icon (`bi-*`) or image, link, button text, order. A used service (form, requests, help requests, specializations) or a non-empty group cannot be deleted. Old `admin/categories` and `admin/sub-categories` pages redirect here.

## Free site check «اختبر موقعك مجاناً» (client file, service 2 — homepage card 2)
- Public, no login (user decision): `/site-test` (`front/SiteTestController`, views `website/site-tests/*`). `SiteUrlGuard` allows only public http(s) URLs (no credentials, ports 80/443, DNS must resolve to public IPs). Per-IP hourly limit from settings. `SiteTestService::start` → `RunSiteTest` job (needs `queue:work`) → engine per device → `site_test_results` (raw JSON kept), `site_test_issues` (one row per audit, worst device; `source` tool|team; priority from the admin rule, else score < 0.5 = high). A failed check is `failed` and never shows a report. A re-check is a new row with `parent_id`.
- Engine: `SiteTestEngine` → `PageSpeedEngine` (PSI v5, `locale=ar`, key `services.pagespeed.key` = `PAGESPEED_API_KEY`; «استخدام الهاتف» scored from viewport/font-size/tap-targets/content-width); tests bind `Tests\Fakes\FakeSiteTestEngine` and a `SiteUrlGuard` without DNS.
- Access to a result: `?t=<token>` link, the session that started it, the owner, or an admin. Contact data only via the full-report form (`requestReport`, phone required, email optional).
- Offer card: shown when `suggested_sub_category_id` is set (first shown issue that has a rule in `site_test_rules`, or chosen by the admin), immediately or after the report is sent (setting). «no» → saved + red admin notification; «yes» → saved + green, then `site-tests.execute` (login, client accounts only, asks only missing contact fields) → `createRequest` makes ONE open `ServiceRequest` (`site_test_id`, problem = URL + top issues with evidence, no contact data) published to freelancers; idempotent under row locks. `SiteTestNotification` data `tone` colours the admin bell.
- Admin: `admin/site-tests` (filters per spec page 9), detail (scores, raw download, issues show/hide, team notes, review summary, suggested service, assignee, send report → email `SiteTestReportReady` + wa.me link), `admin/site-tests/settings` (`SiteTestSettings` in `settings.site_test_settings`, rules CRUD). Texts: content areas `sitetest.page|result`. Starting rules: `php artisan db:seed --class=SiteTestRulesSeeder` (after the catalog seeder).

## Freelancer approval and directory (client file «تعديلات», items 03, 11, 12)
- Freelancers give a WhatsApp number at registration / `account-type` (`User::WHATSAPP_RULE`) and start `freelancer_status = pending`. Everything is free for now (user decision): no OTP provider — the admin checks the number by opening a wa.me chat and marks `whatsapp_verified_at`.
- `User::isApprovedFreelancer()` (approved + checked number) is required to send offers (`FreelancerRequestController::saveOffer`, offer form hidden; notice partial `freelancer-requests/partials/approval-notice`). `UserFactory::freelancer()` creates approved+checked freelancers; `pendingFreelancer()` new ones.
- Freelancer's page `my/freelancer-profile` (`FreelancerProfileController`): WhatsApp (a new number resets the check), bio, availability, languages, starting price (EGP); a rejected freelancer resubmits by saving.
- Admin `admin/freelancers` (`FreelancerAdminController`): check WhatsApp, professional photo (min 400×400, stored by `App\Support\ImageVariants` as a centred square at 128/256/512 px, never enlarged, `User::avatarUrl($size)`), approve (needs check + photo) / reject (reason shown to the freelancer), «مستقلون موثوقون» (`is_featured`).
- Public `/freelancers` (`FreelancerDirectoryController`): `User::listedFreelancers()` only (approved, checked, photo, active); search, group chips, filters (service, rating, max price, availability, language), sorts; texts = content area `freelancers.page`.

## Runtime requirements
- `QUEUE_CONNECTION=database` — needs `php artisan queue:work` running (also runs the free site checks).
- Scheduler (`app/Console/Kernel.php`) runs every minute for scheduled social posts and campaigns — needs `php artisan schedule:run` cron.

## Auth / roles
- Single `web` guard; role is `users.account_type` plus `users.status`. Use the `User::TYPE_*` constants: `مشتري` = client, `بائع` = freelancer, `موظف` = employee (public employees directory), `admin`. Users can only self-select `User::SELF_SELECTABLE_TYPES` (never admin).
- Registration requires choosing client or freelancer. Google sign-ups and old accounts with no type are sent to `account-type`; the `account.type` middleware enforces this on routes that need a type.
- Freelancer specializations: `freelancer_specializations` pivot (user ↔ sub_categories), `$user->specializations()`, managed at `my/specializations`.
- Admin routes are behind `['auth', 'admin']`; `admin` = `App\Http\Middleware\EnsureUserIsAdmin` (active `account_type == 'admin'`, else 403). Any new admin route must go inside that group.

## Settings
- Single row, read with `Setting::first()`. `website_commission` (percent, string) is the site commission; `repeat_client_threshold` (default 2) defines a «repeat client». Both edited in admin `public_settings`.

## Conventions
- Match existing style: controllers grouped with `Route::controller(...)->group(...)`, Arabic validation messages inline in controllers.
- New schema changes go through migrations in `database/migrations`. Columns that legacy code used without a migration were added by `2026_10_20_100000_add_missing_legacy_columns` (guarded with `hasColumn`, safe on a server that already has them). The `reviews` table holds testimonials (`client_name`, `rating`, `content`, `is_approved`).
- Tests: `php artisan test`. Runs on in-memory SQLite (`phpunit.xml`), never touches the MySQL DB; use `RefreshDatabase` for DB tests. All migrations must stay SQLite-compatible (avoid raw MySQL `DB::statement`). `UserFactory` defaults to a client and has `freelancer()`, `admin()` and `inactive()` states.
