# نفّذها (Nafizha) — nafizha.com

Arabic-first services marketplace + LMS + marketing tools. Repo/DB name is `marwa_services`.

## Stack
- Laravel 11 (old-style skeleton: `app/Http/Kernel.php`, `app/Console/Kernel.php`, `RouteServiceProvider`), PHP 8.2+ (local: Herd Lite PHP 8.3)
- Livewire 3 + Alpine.js, Blade views, Vite
- MySQL, Pusher (broadcast/chat), EasyKash (payments), OpenAI (`openai-php/laravel`), Google API (Gmail + Sheets), Socialite
- Localization via `mcamara/laravel-localization` (`lang/ar`, `lang/en`); UI text is mostly Arabic

## Layout
- `routes/web.php` — public site + user area (wrapped in localization group). It `include`s `routes/admin.php` at the end.
- `routes/admin.php` — admin panel under `/admin`.
- Controllers: `app/Http/Controllers/front/*` (site), `app/Http/Controllers/admin/*` (panel), `api/EmailTrackingController` (open/click tracking).
- Models: `app/Models/front/*`, `app/Models/admin/*`, plus top-level models for newer features (Email*, Social*, NewCourse*, Testimonial, User).
- Views: `resources/views/website/*`, `resources/views/admin/*`.
- Uploaded files live under `public/uploads` / `public/assets/uploads` — never under `storage/` (user decision 2026-10-16). Private files (service request files, offer files, product upload chunks, Livewire temporary uploads) use the `private_uploads` disk = `public/uploads/private`, closed by `public/uploads/private/.htaccess` (Apache; on nginx add `location ^~ /uploads/private/ { deny all; }`); they are downloaded only through controllers that check access.
- Navbar (client file «تعديلات», item 02): «المستقلين» (`freelancers.index`, the approved-freelancers directory) and «المدونة» (`blogCategories` = `/blog`; `/categories` is the service categories page) replaced the course links; course links are not shown anywhere (pages still exist by URL). Homepage payment row shows EasyKash methods only.

## Feature areas
- Services/categories, cart & EasyKash checkout, digital products
- Jobs, packages/subscriptions (the old projects & offers system is gone; see Service request system)
- Courses: legacy `courses` and the newer `new-courses` (course → topic → lesson; video protected by `VideoProtectionMiddleware`)
- Properties & property maintenance, blog, portfolio, reviews/testimonials
- Chat (Livewire `app/Livewire/Chat` + Pusher), support tickets, user balance & withdrawals
- **Social media publishing** (`app/Services/SocialMedia/Platforms`: Facebook, Instagram, LinkedIn, TikTok, Twitter, YouTube) via `PublishSocialPostJob`
- **Email marketing** (MailMentor-like, client request): lists/contacts, templates, campaigns with A/B, drip, throttling, follow-ups, tracking, analytics, Gmail sending, Google Sheets import, AI writing (`app/Services/Email*`, `app/Jobs/*Campaign*`)

## Service request system (replaced the old projects/offers system)
- Spec: client PDF «رسم مسار العميل والأدمن والمستقلين»; built in phases (0 accounts/specializations ✓, 1 form builder ✓, 2 request page ✓, 3 freelancer board + offers + chat ✓, 4 payment/escrow + completion ✓, 5 admin tools ✓, 6 client classifications + client↔team messages ✓, 7 old projects/offers removed ✓ (tables dropped by `2026_10_17_100000_drop_old_projects_system`; `projects`, `project/*`, `my/project/*`, `admin/projects` redirect 301). Still to come from the client: the other two homepage cards («شخّص مشروعك مجانًا», «مشروعك ما بيوقف»).
- Requests: `ServiceRequest` (number `REQ-<1000+id>`, route key = number; path execute|explore; status open|inquiry; contact_* never shown to freelancers; filter columns budget_min/max, deadline, project_type, work_mode, city, urgency, experience) → `ServiceRequestAnswer` (snapshot of section/label/type + JSON value) and `ServiceRequestFile` (`private_uploads` disk under `service-requests/<id>/`, downloaded through `requests.file`).
- `App\Services\ServiceRequests\RequestSubmission` = server-side visibility + validation + storing; keep it in sync with the JS. Client pages: `request` (create), `my/requests` (`front/ServiceRequestController`), clients only.
- Request forms: one main `ServiceForm` per sub-category (draft/published/paused; query with `ServiceForm::main()` — a published form may also have one draft revision, `revision_of_id`, edited in the builder `admin/request-forms/{form}/builder` and swapped in by `publishRevision()`) → `ServiceFormSection` → `ServiceFormQuestion` (12 types in `ServiceFormQuestion::TYPES`, `options`/`settings`/`condition`/`filter_key` columns). Admin builder at `admin/request-forms` (`admin/ServiceForm*Controller`).
- A question's `condition` = `{question_id, values[], negate}`: shown only when the source question is visible, answered, and its answer matches (or, with negate, doesn't match). `public/assets/website/js/service-request-form.js` implements this client-side; server validation must apply the same rule.
- Client-facing form markup is shared: `resources/views/website/service-requests/partials/{form-fields,question}.blade.php` (inputs `answers[<id>]`, files `answer_files[<id>][]`).
- Offers: `RequestOffer` (one per freelancer per request, unique; status new→viewed→in_discussion, withdrawn; accepted/rejected come with payment), `RequestOfferFile` (private disk), `OfferMessage` (conversation per offer, stores request + offer ids). Freelancer pages: `client-requests` board/detail, `my/offers` (`front/FreelancerRequestController`); shared chat/files/save: `front/OfferController`. Visibility: `ServiceRequest::scopeForFreelancer()` / `visibleToFreelancer()`; contact_* fields are never rendered on freelancer pages.
- **All payments on the site go through EasyKash** (same integration as the AyaKids project, own Nafizha account), in EGP — Stripe was removed completely (package, routes, views). Every payment is an `online_payments` row (`App\Models\OnlinePayment`; its id = EasyKash customerReference) with a `purpose`: `request` (escrow below), `service_order` (one service from its page or the whole cart — `checkout/order`; payload `items` with prices from the DB, cart emptied once paid; the buyer pays the service prices and the commission comes out of the sellers' share), `product_order`, `package`, `course`, `balance`. `App\Services\Payments\OnlinePaymentService` — `start`/`create`+`checkout`, `sync` (inquiry), `apply` (idempotent: marks paid once under a row lock and calls the purpose's `paid()` inside the same transaction; refuses an amount below the price; a late failure never undoes a payment). Applied from the return page `payments.return` (`payments/return/{id}/{return_token}` — the token replaces the session, the query string is never trusted), `easykash/webhook` (`OnlinePaymentController`, CSRF-exempt, outside the locale group; the payload is only a trigger — the payment is always confirmed by an EasyKash inquiry; the HMAC signature is checked only when `EASYKASH_HMAC_SECRET` is set, which the EasyKash dashboard may not offer) and `payments:sync` every 5 min (Fawry/wallet payments can complete hours later). Purposes implement `App\Services\Payments\PaymentPurpose` (`paid`, `failed`, `response`); the direct purchases live in `App\Services\Payments\Purposes\*` (extend `SitePurpose`; mails/notifications are sent via `afterCommit` so a mail failure never undoes a payment; commission rate is snapshotted in the payload). Prices of services/products/courses/packages are treated as EGP and shown with ج.م. Request escrow: `RequestPaymentService` (also the `request` purpose) — `startCheckout` (pending `RequestPayment` + its OnlinePayment, `request_payments.online_payment_id`, `gateway_reference` = that id), `fulfill` (test helper → `apply`), a payment for an already-taken request becomes `conflict` = needs refund, `deliver`, `release` (freelancer `users.balance` += amount − commission, `settings.website_balance` += commission, rows in `wallet_transactions`), static `commissionRate()` (admin setting, default 10%). EasyKash has no refund API: refunds are done in the EasyKash dashboard and confirmed by the admin (`refund_reference = manual`). Gateway interface `PaymentGateway` (takes an `OnlinePayment`) → `EasyKashPaymentGateway` (config `services.easykash`: EASYKASH_API_KEY, optional EASYKASH_HMAC_SECRET); tests bind `Tests\Fakes\FakePaymentGateway`. Amounts are shown with `App\Support\Money::format()`. Request statuses: open → in_progress → completed.
- Admin tools: `admin/requests?tab=active|inquiries|followup|completed|not_completed|refunds` + `admin/requests/{number}` (`admin/ServiceRequestAdminController`), actions in `App\Services\ServiceRequests\RequestAdminService` (close with `ServiceRequest::CLOSE_REASONS` → status not_completed, «other» needs a note, refunds held money first via `RequestPaymentService::refund`; publish inquiry with client consent; price inquiries use the same follow-up status/note as no-offer alerts (no status = «جديد», filter on the inquiries tab); complete on behalf; follow-up). `requests:alert-no-offers` (scheduled every minute) alerts admins once per request after 60 min without offers; the first offer afterwards marks the follow-up resolved. Admin header bell = `admin/layouts/partials/notifications`. Clients can cancel open/inquiry requests (`requests.cancel`).
- History: `ServiceRequestEvent` (`service_request_events`) logs creation, every status change (model `updated` hook; actor = logged-in user, null = system; set `$request->statusChangeNote` before an update to attach a note), follow-up updates, admin notes and invitations; shown as «سجل الطلب» on the admin request page. Admins see matching freelancers of an open request and invite each once (`RequestAdminService::matchingFreelancers/invite`, route `admin.requests.invite`). Optional `service_requests.contact_method` (`ServiceRequest::CONTACT_METHODS`). Client offer tabs: all/new/saved/discussion/selected/rejected; offer cards show the freelancer's photo and rating (`rate`/`rating_count`).
- Editing (client decision 2026-10-16, «like Upwork»): while open/inquiry the owner edits the whole request (`requests.edit|update`, view `service-requests/edit`; the form partials are pre-filled through `session()->now('_old_input')`; `RequestSubmission::editing($request)->validate()` keeps the path and counts kept files, `update()` replaces answers/filters, removes `remove_files[]`, returns the changed labels) → `service_requests.edited_at`, event `edited`, bidders notified, offers flagged by `RequestOffer::requestEditedSince()` (`request_offers.submitted_at`, set by `saveOffer`). After work starts: `ServiceRequestChange` (`service_request_changes`; pending → awaiting_payment → applied | rejected | cancelled, one open at a time) via `App\Services\ServiceRequests\RequestChangeService` (`propose`, `respond` by the chosen freelancer, `payFromBalance`, `startCheckout`, `cancel`, `differencePaid`). Higher price: a second `RequestPayment` with `service_request_change_id` (gateway `easykash` or `balance`), applied when paid (late payment for a cancelled change = `conflict`). Lower price: `refunded_amount` on the held payments (newest first), commission/freelancer share recomputed, difference to the client's `users.balance`. `service_requests.agreed_price` = current price (`currentPrice()`, `moneyTotals()`); `release()` pays every held payment, `refund()` refunds the net amount (balance-paid → back to the balance), closing refunds all held payments and cancels open changes. UI partial `service-requests/partials/changes` (client + freelancer), admin card «طلبات التعديل بعد البدء». Email key `request_changes`.
- Admin guide page: `admin/requests-guide` (`admin/service-requests/guide.blade.php`) — keep it in sync when behaviour changes. Demo data (non-production only): `php artisan db:seed --class=ServiceRequestsDemoSeeder` (accounts demo-*@nafizha.test, password `password`).
- The client's request page shows a timeline (`service-requests/partials/timeline`: sent → open → offers → chosen → done / not completed).
- Double submit: `ServiceRequestController::store` takes a 30 s cache lock on a fingerprint of the submitted fields (no files); a repeat redirects to the request just created. The JS also blocks a second submit.
- The request page autosaves a draft (not files) in localStorage `rf-draft:<user id>`, restored on return and cleared after a successful submit (`request_created` flash).
- Client↔team messages: `RequestAdminMessage` (per request, `from_admin`), boxes on the client request page (`requests.messages.store`) and the admin request page (`admin.requests.messages.store`); never shown to freelancers.
- Client classifications: `App\Services\ServiceRequests\ClientClassifier` computes the 7 categories (fixed order in `CATEGORIES`) from requests + who spoke last in each team conversation; repeat threshold = `settings.repeat_client_threshold`; `settings.client_count_mode` (`ClientClassifier::COUNT_MODES`: requests only, or requests + «ساعدوني أختار» help requests — a help-only user then counts as a client) and `settings.client_tags_overlap` (false = «متكرر» replaces «ثاني مرة») are admin choices in `public_settings`; `classify()` returns `requests` and `contacts`. Admin pages `admin/clients`, `admin/clients/{user}` (`admin/ClientController`).
- Email per notification type is a site setting (`settings.request_notification_emails`, `App\Services\ServiceRequests\NotificationSettings`); each notification class names its `$emailKey`. Client classifications are cached 5 min (`ClientClassifier::cached()`), cleared by ServiceRequest / RequestAdminMessage / Setting model events.
- Notifications for this system extend `App\Notifications\ServiceRequestNotification` (data `text` + `url` path; bell entry sync, email queued). The navbar bell renders any notification with `data.url` generically and opens it via `notifications.open` (marks read, same-site paths only).
- Site CSS: the theme's forced white button text (`button { color:#fff !important }`) skips classes starting with `rf-`, so request-system buttons set their own colours; laravel-notify's CSS is loaded before the theme (website + admin). The theme still styles every `[type=radio|checkbox] + label` — scope new styles under a container class (see `.rf-*` / `.account-type-*` in `public/assets/website/css/styles.css`).

## Service 3 «مشروعك ما بيوقف»
- All client decisions are in the questions doc (https://claude.ai/code/artifact/c0af46d6-5743-4441-8752-d1ee9febb3e0, all answered 2026-10-16). Built in 6 phases, all done (2026-10-16): 1 staged project + choosing a freelancer, 2 agreement, 3 stages/funding/delivery/review, 4 clock/lateness/reminders, 5 disputes + freelancer change, 6 roles/ratings/dispute policy.
- Phase 1: a `ServiceRequest` with `kind = staged` (`project_title`, `stopped_project` + `done_before` for projects started outside Nafizha — offers on the remaining part only). Page `staged-project` (`requests.staged` = `ServiceRequestController::createStaged`, the create view in staged mode + `partials/staged-fields`; texts = content areas `staged.page|staged.steps`); homepage card 3 and the landing starter card link there. Always published (no inquiry path). Board/admin show «مشروع بمراحل». Choosing an offer (`offers.accept`) on a staged request does NOT pay: `App\Services\Contracts\StagedProjectService::chooseOffer` accepts the offer, rejects the others, sets the request in_progress + `agreed_price`, and opens a `Contract` with status `agreement` (`ServiceRequest::contract()`); pages show `partials/staged-status` instead of the pay-once progress.
- Phase 2 (agreement): `ContractAgreement` (`contract_agreements`, versions per contract: proposed → changes_requested | approved, older ones superseded; scope, out_of_scope, client_materials, stages JSON `[{title, deliverable, duration_days, amount, revisions|null=unlimited}]` (default 2 revisions, max 10 stages), total = sum, freelancer/client approval times + client IP). `App\Services\Contracts\AgreementService`: `propose` (contract freelancer, while the contract is `agreement`), `requestChanges` / `approve` (client, latest proposed version only); approval creates the `ContractStage` rows (with deliverable, duration_days, revisions), sets the contract `active` and the request's `agreed_price` = total; every step is logged as request event `agreement` and notified (email key `contracts`). Page `contracts/{contract:number}` (`front/ContractController`, view `website/contracts/show` + `partials/stage-row`): client, contract freelancer or admin only. Durations are in days because the clock starts after approval + first funding + client materials (phase 4 pauses/lateness move deadlines).
- Phase 3 (stages): `App\Services\Contracts\StageWorkflow` — current stage = first not settled; `advance()` starts it when funded (sets `started_at`, `due_at` = start + `duration_days`; called after balance funding, in `ContractStagePurpose::paid`, and after each approval), `deliver` (current started funded stage, one pending delivery at a time; `ContractDelivery` note + links + `ContractDeliveryFile` on `private_uploads` under `contracts/<id>/stage-<id>`, ≤10 files × 20 MB, review due in 5 days), `approve` (ContractLedger::release, next stage advances; the last approval completes the contract and the request), `requestRevision` (within `revisions`, `revisions_used`; none left → addendum or dispute). Contract page actions: `contracts.fund` (several stages, `source` balance|easykash), `contracts.deliver`, `contracts.review` (approve|revision), `contracts.file`; view partial `contracts/partials/stages-board`. The request page's `staged-status` follows progress.
- Phase 4 (clock): `ContractPause` (`contract_pauses`: freelancer's exact request, active → resumed | objected, `extended_minutes`) via `App\Services\Contracts\StageClock` — `pause` (current running stage, none pending review, one at a time), `answer` (client note + files → `contract_delivery_files.contract_pause_id`, resumes and moves `due_at` by the paused time), `resumeByFreelancer`, `object` (ends without extension, admins alerted), `endOnDelivery`. `tick()` = command `contracts:deadlines` (every 15 min): due reminder a day before, late alert to freelancer/client/admins, 7 late days → client may ask to change the freelancer (admins alerted), review reminder after 3 days and admins after 5 (never auto-approved), pause reminder after 3 days and admins after 7 — each once (timestamps on stages/deliveries/pauses); paused stages or stages waiting for review are never late. UI partial `contracts/partials/stage-clock`.
- Phase 5 (disputes + freelancer change): `ContractDispute` (`contract_disputes`: reason from `REASONS`, description, evidence files via `contract_delivery_files.contract_dispute_id`, open → awaiting_decision (answered, or after 3 days by `contracts:deadlines`) → decided | withdrawn; one open per contract; its stage money is frozen — client approval/revision and pauses are refused). `App\Services\Contracts\DisputeService` (`open`, `respond`, `withdraw`, `decide`: continue | revision (new deadline, no client revision used) | release | refund | split % | change_freelancer — each with a written reason; settlements go through `StageWorkflow::afterSettlement`). `ContractFreelancerChange` (`contract_freelancer_changes`: client after 7 late days / freelancer withdrawal / admin; always decided by the admin) via `FreelancerChangeService::request|reject|apply`: the leaving freelancer gets the admin-set % of the current unapproved stage (rest to the client's balance), prefunded stages are refunded to the balance, the contract becomes `replaced`, its request `not_completed` (`freelancer_replaced`), and a continuation staged request (`continues_contract_id`, answers + original and delivered files copied, «what was done/remains» in `done_before`) is published for new offers → new contract/agreement = the addendum. Admin: decisions on the contract page (`contracts.disputes.action` decide, `contracts.change.decide`), list `admin/contracts` (`admin/ContractAdminController`, tabs disputes/changes/late/reviews). UI partials `contracts/partials/disputes|change-decision`.
- Phase 6: staff roles `users.admin_role` (`App\Support\StaffPermissions`: manager = null/`manager`, `disputes` reviewer, `accounts`; `mode()` → direct | propose | deny, `canApprove()`; money decisions = release/refund/split/change_freelancer; above `settings.contract_approval_threshold` (0 = no limit) only the manager approves). A proposal is stored on the dispute/change (`proposed` JSON + `proposed_by`) and carried out by `DisputeService::settleProposal` / `contracts.change.proposal`. Roles page `admin/staff-roles` (manager only, one manager always kept). Ratings `ContractRating` (`contract_ratings`, once per side after completion via `RatingService`): client → freelancer updates `users.rate` + `rating_count` (directory), freelancer → client updates `users.client_rating|client_rating_count` (shown to freelancers on request pages, never to the client); one reminder 2 days after `contracts.completed_at`. Public policy page `dispute-policy` (`policy.disputes`, content areas `policy.page|policy.items`, linked from the agreement approval and the dispute form).
- Audit additions: stage `acceptance` («معيار القبول», optional, in the agreement JSON and `contract_stages`); a new proposal starts from `ContractAgreement::defaultStages()` (3 stages, 30/40/30 of the offer); funding (balance or EasyKash) is logged on the request and notified, a failed EasyKash funding is notified, and `StageWorkflow::advance` asks the client once to fund the next unfunded stage (`contract_stages.funding_requested_at`). «مشاريعي» = `my/projects` (`contracts.index`, tabs active/done, `Contract::involving()`, `nextStep($viewer)` = whose turn), linked from the dashboard sidebar and the navbar menu when the user has a contract.
- Group 3 (audit 2026-10-16): **addendum** `ContractAddendum` (`contract_addenda`, `changes` JSON of add|change|remove — read it with `getAttribute('changes')` inside the model, Eloquent has its own `$changes`) via `App\Services\Contracts\AddendumService` (`propose` by either side, `respond` by the other = applied then, `cancel`; one open at a time; not during a dispute or while a stage is being paid; funded stages only go down → `ContractLedger::lowerHeld` returns the difference to the client's balance; a running stage's duration change moves `due_at`); UI partial `contracts/partials/addenda`, routes `contracts.addenda.*`. **Team tools** `App\Services\Contracts\ContractAdminTools` (`extendDeadline`, `approveForClient` = money → `StaffPermissions::mode` must be direct, `endPause` with/without extension; reason required, logged, both told), partial `contracts/partials/admin-tools`, routes `contracts.admin.*`. **Board** `admin/contracts`: columns current stage/money/deadline/«بانتظار» (`Contract::waitingOn()`, `currentStageLoaded()`), filters status/waiting/dates/search by party, sorts due/value, tabs pauses/addenda. **Policy** `App\Services\Contracts\ContractPolicy` (`settings.contract_policy`: `NUMBERS` deadlines/limits, dispute reasons, stage templates) — read values there, never hard-code; admin `admin/contract-policy` (manager only); `ContractAgreement::defaultStages($price, $days, $template)` uses the templates (`?template=N` on the contract page).
- Lateness: `ContractStage::scopeLateNow` (running, past due, not paused, not waiting for review — admin «late» tab) and `scopeLateForChange` (the client's right to ask for another freelancer: the CURRENT stage late by `late_change_days`); resuming a pause or extending resets the late flags only when the stage is on time again. The contract page says the deadline starts at funding (materials = a clock pause) (user decision 2026-10-17). The site check stays one page (user decision 2026-10-17).
- Audit round 2 (2026-10-17): `Contract::expectedEnd()` on the stages board; the running stage shows «معلّقة بسبب خلاف» during an open dispute; no funding while a freelancer change is pending (`ContractLedger::fundable`). Team: `ContractReplyRequest` (`contract_reply_requests`, «طلب رد من الطرفين بمهلة», `ContractAdminTools::requestReply|reply|closeReply|tick` — overdue alert once via `contracts:deadlines`), partials `contracts/partials/reply-requests` (both sides) and `admin-summary` (admins: last delivery / client action, money movements + EasyKash references, project log). `ContractPolicy::save` logs `contract_policy_changes` (who, before → after; shown on the policy page); `due_reminder_days` setting; stage templates take an optional 4th column «معيار القبول». Admin board: «آخر نشاط» column (last request event) and service filter.
- `Contract` (`contracts`, number `CNT-<1000+id>`, client, current `freelancer_id`, optional `service_request_id`) → `ContractStage` (`contract_stages`: unfunded → funding → funded → released | refunded | split; `commission_rate` fixed at funding; `released_to`, `released_amount`, `commission_amount`, `freelancer_amount`, `refunded_amount`). Ledger rows in `wallet_transactions.contract_stage_id`.
- `App\Services\Contracts\ContractLedger`: `fundFromBalance` (several stages at once, all or nothing), `startFunding` (EasyKash, purpose `contract_stage` → `Purposes\ContractStagePurpose`, amount + `gatewayFee()` = `settings.stage_fee_percent|stage_fee_fixed`, paid by the client, never refunded), `fundingPaid` (money for a stage no longer waiting goes to the client's balance), `release`, `refund` (full amount to the client's site balance, no commission), `split` (commission on the freelancer's part only), `changeFreelancer` (later releases go to the new freelancer). Wording for held money: «يبقى المبلغ لدى نفّذها حتى تعتمد المرحلة» (never «ضمان»).

## Journey analytics (client file «تعديلات», item 08)
- First-party, consent first: nothing is stored before the visitor clicks «موافق» in the banner (`website/layouts/partials/analytics.blade.php`, cookie `analytics_consent` 1/0, POST `analytics.consent`; declining forgets the visit). Bots ignored.
- `App\Services\Analytics\Tracker` (stateless singleton; the current visit is cached on the request): `visit()` (new visit after 30 min idle or a new `utm_source`), `record`, static `recordOn` (keeps the furthest `FUNNEL` step in `analytics_visits.last_step`), `source()` (utm → gclid/fbclid → referrer; a blog landing from search counts as `blog`). Middleware `track.visit` (localized group) records GET HTML pages: `requests.create`, `services.index`, `site-tests.index`, service pages = `service_view`, others `page_view`.
- Funnel events: `service_view` → `form_start` (beacon from any `form[data-track-start]`, `analytics.form-start`) → `cart_add` (`CartController`) → `payment_start` (`OnlinePaymentService::create`, stores `online_payments.visit_id`) → `order_complete` / `payment_failed` (`apply`, also from the webhook/sync). `request_submitted` from the request page. After a failed/cancelled payment the return page flashes `abandon_payment` and the site asks an optional reason (`AnalyticsController::ABANDON_REASONS`, only the same visitor cookie can answer); with no answer the admin sees «السبب غير معروف».
- Admin `admin/analytics` (+ `admin/analytics/visits/{visit}`, `admin/AnalyticsAdminController`): filters date/source/service/status (completed = order_complete or request_submitted; abandoned = last step form_start/cart_add/payment_start; browsing), KPIs, funnel with drop-off, sources, reasons, visits list and per-visit path. `analytics:prune` (daily 03:30) keeps 13 months.

## Conventions
- Match existing style: controllers grouped with `Route::controller(...)->group(...)`, Arabic validation messages inline in controllers.
- New schema changes go through migrations in `database/migrations`.
